# rn-iso field-test protocol

A handoff document for an AI agent testing rn-iso end to end on a real
repository. The deliverable is equal parts "does it work" and a **friction
log** — every rough edge, confusing output, wrong default, or extra step you
needed, however small. You are the target user: an agent doing a dev loop.
Be adversarial. **A PASS you did not actually observe is worse than a FAIL.**

Read this as a checklist, not an essay. Every step names the **evidence** it
must produce. "It seemed to work" is not evidence; a quoted output line, a
number before and a number after, or a file listing is.

## What CI already proves, and what this is for

`test/e2e/native/run-native-e2e.mjs` (the 2x2: `{bare,expo}` x `{ios,android}`)
runs the loop on **freshly created apps**. `test/e2e/cache-flow.e2e.js` runs the
cache library with no compiler at all. Between them, already proven:

| Already proven automatically                                                                            | Where                                                                           |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| start mode per framework (`expo-child` / `bare-inproc`)                                                 | native 2x2                                                                      |
| a cold build produces a real artifact                                                                   | native 2x2                                                                      |
| a second worktree hits the local cache with NO compile (asserted from the build log, not just the JSON) | native 2x2                                                                      |
| `worktree create` / `remove` and the five cleanup checks                                                | native 2x2                                                                      |
| platform-scoped fingerprint parity across two worktrees of one commit                                   | `cache-flow.e2e.js`                                                             |
| single-flight: one of N racing processes compiles, the rest resolve its artifact                        | `cache-flow.e2e.js` — **synthetic artifacts, stubbed fingerprint, no compiler** |

Everything else is yours. CI never touches: a real repo (monorepo, hoisted
deps, dynamic config, committed native dirs, real product flavors), the Metro
transform store's actual contents, the Xcode CAS, Gradle's build cache,
release builds, the remote cache tier, Pods reuse, single-flight with a real
compiler, or `gc`'s report of all of it.

Steps are tagged:

- **[CI]** — covered on fresh apps. Run it on a REAL repo, where it is not covered, or skip it and say so.
- **[MANUAL]** — no automated coverage anywhere. Skipping one is a reportable gap, not a silent omission.

## Setup

```bash
npx rn-iso@latest --version     # must be >= 1.5.0; npx caches stale versions
npx skills add appandflow/rn-iso   # then READ the installed skill before starting
npx rn-iso guide lifecycle      # generated by the binary; cannot be stale
npx rn-iso guide settings       # the zero-config claims, in the binary's own words
```

If this machine ran an earlier build of rn-iso: BEFORE anything else, run `npx rn-iso
status` and `npx rn-iso gc` (report-only) and read both skeptically — compatibility
against state an earlier build wrote is not guaranteed. Old cache dirs
(`~/.rn-iso-build-cache`, `~/.<name>-metro-cache`) are dead and ignored;
stale device records should surface in `gc`, not crash anything. Anything
odd here is a HIGH-severity finding.

## Use a fixture that looks like a real repo

A fresh `create-expo-app` has never been prebuilt, so its `app.json` carries no
`ios.bundleIdentifier` / `android.package` and its `package.json` still has the
`expo start` scripts. The first prebuild writes all three -- TRACKED files --
which moves the fingerprint and makes a cold worktree miss a cache entry it
would otherwise hit. A real CNG repo has those values committed (Expo
recommends setting them explicitly), so prebuild writes nothing tracked and a
cold worktree hits on its first lookup; a bare repo commits `ios/` and
`android/` outright and never prebuilds at all.

So before testing anything about caching across worktrees: **prebuild once and
commit on the main tree** (or set those keys by hand). Otherwise the fixture
manufactures a transition that few users ever see, and the result reads as a
product bug. Test the cold/warm split deliberately, when it IS the thing under
test.

## Safety rules (non-negotiable)

- NEVER modify the target repo's main checkout. Worktrees only.
- NEVER run `gc --delete` or `gc --delete --all` without the user's explicit
  approval in this session. Bare `gc` (report) is always fine.
- Touch no simulator/emulator except `rn-iso-*` ones YOUR runs created.
- No raw `simctl recordVideo` (it can wedge a machine with a global lock);
  record only through your device tool's own mechanism, prefer screenshots.
- No commits or pushes in the user's repos. Clean up everything you create.

## Evidence helpers

Every cache assertion below uses these. Paste the output verbatim into the
report; do not paraphrase a number.

```bash
CFG=${RN_ISO_HOME:-$HOME/.rn-iso}
BUILD_CACHE=${RN_ISO_BUILD_CACHE:-$CFG/build-cache}
CAS=$CFG/compilation-cache
GRADLE_CACHE=${GRADLE_USER_HOME:-$HOME/.gradle}/caches/build-cache-1
# The Metro store root: READ IT from the log record (below), do not derive it.
# The path segment is the package name with every non [A-Za-z0-9._-] run
# replaced by "-", so "@acme/app" becomes "-acme-app".

# One measurement: kilobytes, file count, files newer than the marker.
snap() { printf '%s\n  %sKB  %s files  %s newer than marker\n' "$1" \
  "$(du -sk "$1" 2>/dev/null | cut -f1)" \
  "$(find "$1" -type f 2>/dev/null | wc -l | tr -d ' ')" \
  "$(find "$1" -type f -newer /tmp/rn-iso-qa.marker 2>/dev/null | wc -l | tr -d ' ')"; }

touch /tmp/rn-iso-qa.marker   # reset immediately BEFORE each measured step
```

**A cache that is engaged and does not grow is a silent no-op.** That is
exactly how the Metro-shim bug (#73) shipped through green CI and was caught
only by measuring a directory. Treat "the flag was passed" and "the cache
filled" as two separate questions, always.

## The test script

Deviate when reality demands it — and log why as a friction.

1. **Orient.** `status` (what is already on this machine), `doctor` in the
   app dir (report findings; judge whether each is true of this repo).
   **[CI]** for the mechanics; the judgement is yours.
2. **Baseline the tree** (do this before anything writes). **[MANUAL]**
   ```bash
   git -C <repo> status --porcelain | tee /tmp/rn-iso-qa.porcelain-before
   git -C <repo> worktree list
   ```
3. **Workspace.** `cd "$(npx rn-iso worktree create <name> --carry-ignored)"`.
   Note whether `--base <ref>` works if you need a specific commit, whether
   the stderr said what it branched from, and what `--carry-ignored`
   reported. Install deps with the repo's OWN tooling (read its docs;
   monorepos: work from the app directory, but install per the repo's rules).
4. **Dev server.** `npx rn-iso start --json`. Assert: correct mode
   (`expo-child` for Expo apps, `bare-inproc` for bare RN — a wrong detection
   here is CRITICAL), the `.rn-iso/` gitignore entry self-ensured, second
   `start` a no-op, `status` shows the supervisor healthy. **[CI]**
5. **Build.** `npx rn-iso ios` (and/or `android`). Cold: watch the phase
   lines; on failure judge the extracted diagnostic against the raw log in
   `.rn-iso/logs/build-*.ndjson` — was it enough to act on? Assert the
   `--json` payload: `launched` per section E; `cacheHit` false on a genuine
   cold build; `appPath` exists on disk. **[CI]**
6. **Interact.** Drive the app with your device tool (snapshot, screenshot,
   a few taps), targeting YOUR sim by udid, never "booted". No real logins.
7. **Logs.** `logs --errors` on the healthy app (near-empty, exit 0, no OS
   syslog noise). Then break the bundle on purpose (rename an imported
   file), reload, and assert the failure SURFACES in `--errors`; fix it and
   assert it stops being reported after the next bundle. `status`'s error
   count must stay sane throughout.
8. **Sections A through D below**, before teardown — they need live
   workspaces.
9. **Teardown.** `stop` in each, then `worktree remove` each — with NO
   `--force` and NO manual `rm`. A refusal you cannot resolve by following
   the message's own remedy is a HIGH finding.
10. **Verify cleanup**, all five: **[CI]**

- `xcrun simctl list devices | grep rn-iso` → none of yours remain
  (`emulator -list-avds` likewise on Android)
- `ps aux | grep -E 'rn-iso|supervisor'` → no supervisors or collectors
- `npx rn-iso status` → your workspaces gone from the registry
- `git -C <repo> status --porcelain` and `git worktree list` → identical
  to the baseline captured in step 2
- bare `npx rn-iso gc` → nothing orphaned that you created

## A. Zero-config proof, per platform [MANUAL]

The claim under test: **rn-iso needs no project change.** The performance
caches that used to be setup steps are supplied on the command lines rn-iso
composes itself. Each sub-step below proves one half of that: that rn-iso
asked, and that something actually happened.

### A1. The tree is untouched but for one block

```bash
# in the WORKTREE, after start + a build
git status --porcelain
git diff -- .gitignore
```

- Assert: the only rn-iso-authored change is the `.rn-iso/` block appended to
  `.gitignore` (or a whole `.gitignore` created where the repo had none).
  No `metro.config.js`, no `Podfile` / `Podfile.properties.json` edit, no
  `gradle.properties` edit, no `app.json` edit that rn-iso made.
  `expo prebuild` output on a CNG repo is the project's own tooling, not
  rn-iso — call it out separately.
- Then `worktree remove` (step 9) and assert git restored it: the removal
  prints `restoring <path>/.gitignore (only rn-iso's own entry was added)`
  or `removed <path>/.gitignore (rn-iso wrote all of it)`.
- **Evidence:** the porcelain listing before and after, and the removal's own
  line.
- **Known and correct:** on the MAIN checkout, `worktree remove` reclaims the
  environment and deliberately leaves the working tree untouched — so the
  `.gitignore` block PERSISTS there and you must revert it by hand. Verify
  the diff is only that block; a persisting block is expected, anything else
  is CRITICAL.

### A2. The Metro transform store actually gains files

```bash
touch /tmp/rn-iso-qa.marker
snap "$STORE"                 # before
# force a REAL bundle: reload the app, or curl the dev server
curl -s "http://127.0.0.1:<port>/index.bundle?platform=ios&dev=true" > /dev/null
snap "$STORE"                 # after
```

- Assert: KB up, file count up, and "newer than marker" > 0.
- **CRITICAL** if the store is configured (A3/A4 confirm it) and does not
  grow across a real bundle. That is the silent no-op; it has shipped before.

### A3. Expo: the confirming record, and no warning

```bash
npx rn-iso logs --source metro --json | grep -E 'cache_store_(requested|added|skipped|present)'
npx rn-iso logs --source metro --grep 'could not share'
```

- Assert `event: "cache_store_added"` is present. Quote its `msg` — it names
  the store root; that is the `$STORE` A2 measures.
- Assert NO line matching `warning: rn-iso could not share this project's
Metro transform cache`.
- `cache_store_requested` **alone is not evidence.** It says rn-iso set
  `NODE_OPTIONS` on a process it does not run. Only the shim's own
  `cache_store_added`, reported from inside that process, means the store
  reached the config Metro loaded. A run with `requested` and no `added` is
  the exact shape of #73: **CRITICAL**.

### A4. Bare: the same record from the in-process append

Same two queries. On `bare-inproc` the store is appended by rn-iso itself, so
`cache_store_added` is written directly (`appended the shared Metro transform
store at <root> to this project's cacheStores`). `cache_store_present` is an
acceptable pass on a project that already wires up `@rn-iso/metro` by hand —
say which you saw. A2 still has to show growth either way.

### A5. iOS: the five settings on the real xcodebuild argv, and a growing CAS

```bash
npx rn-iso logs --source build --json | grep '"event":"build_start"'
# or straight from the file:
grep -m1 build_start .rn-iso/logs/build-ios.ndjson
```

- Assert all five appear verbatim in that one `xcodebuild ...` line:
  `COMPILATION_CACHE_ENABLE_CACHING=YES`, `COMPILATION_CACHE_CAS_PATH=<CAS>`,
  `SWIFT_ENABLE_COMPILE_CACHE=NO`, `CLANG_ENABLE_PREFIX_MAPPING=YES`,
  `CLANG_OTHER_PREFIX_MAPPINGS=<this workspace root>=/^src`.
- Assert the stderr note appeared: `compilation cache on for this build: CAS
at <path> ...`.
- `snap "$CAS"` before and after the cold compile: it must grow.
- **Expected absences, not failures** (say which applies): Xcode major < 26,
  an unreadable `xcodebuild -version`, or a project with
  `apple.ccacheEnabled=true` in `ios/Podfile.properties.json` all correctly
  produce ZERO settings. Assert the argv then carries none of them, rather
  than reporting a bug.
- **Evidence:** the quoted argv line, the note, both `snap` lines.

### A6. Android: `--build-cache` on the real gradlew argv

rn-iso writes a `build_start` record with the full argv on iOS only —
`build-android.ndjson` holds gradle's transcript but never gradle's own
command line. So catch it from the process table while the build runs:

```bash
npx rn-iso android --json > /tmp/qa-android.json 2>/tmp/qa-android.err &
for i in $(seq 1 150); do ps -o args= -ax | grep '[g]radlew' && break; sleep 2; done
wait
grep 'gradle build cache on for this build' /tmp/qa-android.err
```

- Assert the captured argv ends in `assemble<Variant> --build-cache`, and
  that the dim note is on stderr.
- `snap "$GRADLE_CACHE"` before and after: it must grow.
- Cross-worktree reuse is B5.
- **Papercut worth filing:** the argv asymmetry itself. iOS logs its command,
  Android does not, so this assertion needs a process-table race that iOS's
  does not.

## B. Every cache, three proofs [MANUAL unless tagged]

Every cache gets the SAME three questions. Fill this table in the report with
your own values; a blank cell is a gap, not a pass.

| Cache                              | 1. ENGAGED (quote it)                                                   | 2. STORES (measure it)                                                                   | 3. REUSED (prove it)                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| B1 Fingerprint build cache (local) | `fingerprint <hash> miss` on the cold run                               | a new `$BUILD_CACHE/<platform>/<key>/` holding the artifact + `fingerprint-sources.json` | wt2: `fingerprint <hash> hit`, build log holds only the launch record                     |
| B2 Remote build-cache tier         | `cache  remote miss (<name>)` / `remote hit (<name>) -> stored locally` | after a remote hit, the LOCAL entry exists                                               | a third workspace hits level one, no provider call                                        |
| B3 Metro transform store           | `cache_store_added`, no "could not share" warning                       | A2's `snap` growth                                                                       | wt2's first bundle adds far fewer files than wt1's did                                    |
| B4 Xcode compilation cache (CAS)   | the five settings on the `build_start` argv                             | `snap "$CAS"` growth over the cold compile                                               | wt2's forced compile faster than wt1's cold compile (state both numbers)                  |
| B5 Gradle build cache              | `--build-cache` on the captured gradlew argv                            | `snap "$GRADLE_CACHE"` growth                                                            | `FROM-CACHE` task lines in wt2's `build-android.ndjson`                                   |
| B6 Pods reuse                      | no `pods` phase line at all                                             | n/a (carried, not stored)                                                                | wt2 with matching Pods never runs `pod install`                                           |
| B7 Single-flight dedup             | `<root> is already building <hash> (pid N)`                             | n/a (it stores through B1)                                                               | `waited <d> for <root>'s build -> installed from cache` + `waitedForBuild` in the payload |
| B8 `gc`'s view                     | `Shared build caches (N) - alive, not garbage:`                         | each row's size is non-zero and the dir is right                                         | `--delete --older-than N` trims only what it named                                        |

### B1. Fingerprint build cache (local) [CI on fresh apps]

Second worktree, same commit, fresh install, `start`, then the build command.

- Assert `fingerprint <hash> hit` and install-without-compile: the build log
  holds only the launch record and NO `xcodebuild` / `CompileC` / `Ld ` (iOS)
  or `gradlew` / `:app:compile` / `Task :app:` (Android).
- Assert the stored entry's sidecars:
  ```bash
  ls -la "$BUILD_CACHE/<platform>/<key>/"
  ```
  `fingerprint-sources.json` must be there. On an **Android release** entry,
  `assets-manifest.json` must be there too — without it the release asset
  gate refuses every swap (see C4), which reads as a perpetual cache miss.
- On a CNG repo, watch for the post-mutation store: prebuild and `pod install`
  move the hash, and the run says
  `<a> -> <b> after prebuild + pod install; storing under the new key, which
is the one the next run looks up`. **The entry must be keyed on the SECOND
  hash.** An entry under the pre-mutation key is a cache no cold worktree can
  ever hit: CRITICAL.
- A MISS with a diagnosed cause is a critical finding to report, not to bury.
  Quote the fingerprint line's named files, and the full diff from the build
  log.

### B2. Remote build-cache tier

Only meaningful on an Expo project that configures `buildCacheProvider`
(`"eas"`, or its own module). A bare RN project has no provider concept and
rn-iso correctly never calls one — assert that silence rather than a miss.

- Force a local miss (`--no-build-cache`, or a fresh `RN_ISO_BUILD_CACHE`) and
  assert the tier is consulted only THEN, and is time-bounded (resolve 30s,
  upload 60s, config 30s). Quote `remote hit` / `remote miss` / the
  `did not answer within ...; building instead` line.
- On a remote HIT: assert `-> stored locally` and that
  `$BUILD_CACHE/<platform>/<key>/` now exists. That copy-on-the-way-past is
  the whole point; a hit that does not land locally makes every later
  worktree pay the download again.
- On a fresh build: assert the upload is started and reported (`cache
uploaded (<name>)`), and that it did NOT serialize with the install.
- **Account mismatch.** On a repo whose `expo.owner` is not an account the
  session belongs to, assert the documented warning appears verbatim and the
  run CONTINUES:
  `eas is authenticated as <account>, and this project's owner is <owner> --
run 'eas login' as a member of <owner> (or set EXPO_TOKEN); consulting the
EAS cache anyway`
  A definitively logged-out machine instead prints `eas is not authenticated
... building with the local cache only` and skips the tier.
- **UNVERIFIABLE WITHOUT A MATCHING ACCOUNT:** an actual remote hit, an actual
  upload, and the download-into-local path. Say so plainly in the report
  rather than marking them passed. What you CAN verify without an account:
  the miss path, both auth warnings, the timeout, and that a provider failure
  never fails the build.

### B3. Metro transform store, per mode

A2/A3/A4 cover engaged + stores. For reuse:

- With wt1's store already warm, bundle the same app in wt2 (`snap` around
  it, marker reset first).
- Assert: wt2's cold bundle is markedly faster than wt1's was, OR the file
  count grows by far less than wt1's growth. Both numbers go in the report.
- Honest caveat: transform keys include the project root only if the
  project's own config puts it there. If the second bundle grows by roughly
  the same amount as the first, that is a real finding (the store is
  per-worktree in effect), not a measurement error — file it HIGH with both
  counts.
- Both modes must be exercised across the QA matrix: `expo-child` (shim) and
  `bare-inproc` (in-process append).

### B4. Xcode compilation cache (CAS)

A5 covers engaged + stores. For reuse, rn-iso's own tier would short-circuit
wt2 entirely, so force a compile:

```bash
npx rn-iso ios --no-build-cache --json    # in wt2, same commit
```

- Compare `durationMs` against wt1's cold build. State both numbers.
- **Say so honestly if the delta cannot be isolated.** `SWIFT_ENABLE_COMPILE_CACHE=NO`
  means only clang is cached, so on a Swift-heavy project the delta is modest
  by design. A modest, stated delta is a pass. An unmeasured "seems faster"
  is not.
- The CAS must still have grown, and `CLANG_OTHER_PREFIX_MAPPINGS` must name
  **wt2's own root** (not wt1's) — that remapping is the only reason the two
  compute the same keys.

### B5. Gradle build cache

A6 covers engaged + stores. For reuse:

```bash
npx rn-iso android --no-build-cache --json   # wt2, same commit: forces gradle to run
grep -c 'FROM-CACHE' .rn-iso/logs/build-android.ndjson
npx rn-iso logs --source build --grep 'FROM-CACHE' --tail 20
```

- Assert a non-zero count of `FROM-CACHE` tasks and quote a few.
- `--no-build-cache` turns off **rn-iso's own** fingerprint tier, not
  gradle's `--build-cache` — that flag is still on the argv. Without it, the
  fingerprint hit installs the APK and gradle never runs at all, so there is
  nothing to observe. Note this in the report so the next tester does not
  read "no FROM-CACHE lines" as a failure of the wrong cache.
- Zero `FROM-CACHE` on a forced second build at the same commit is
  **CRITICAL**: the flag is on the line and the cache is doing nothing.

### B6. Pods reuse

- Create wt2 with `--carry-ignored` from a source tree whose Pods are
  installed and current. Assert `rn-iso ios` prints **no `pods` phase line at
  all** — the decision is silent when there is nothing to do.
- Then break it deliberately (e.g. `rm ios/Pods/Manifest.lock`) and assert the
  reinstall is announced with its reason:
  `pods  ios/Pods/Manifest.lock is missing (pods have never been installed
here) -> installed (<d>)`. The other two reasons are
  `ios/Podfile.lock is missing but ios/Pods exists` and
  `ios/Podfile.lock and ios/Pods/Manifest.lock differ`.
- A `pod install` on every build of an unchanged tree is HIGH: it is minutes
  per run and it dirties tracked files.

### B7. Single-flight dedup [CI at the library level only]

`cache-flow.e2e.js` proves the lock with synthetic artifacts. Prove it with a
real compiler:

```bash
# two worktrees, same commit, both cold (clear or redirect $BUILD_CACHE first)
( cd "$WT1" && npx rn-iso ios --json > /tmp/qa-wt1.json ) &
sleep 5
( cd "$WT2" && npx rn-iso ios --json > /tmp/qa-wt2.json ) &
wait
```

- Assert exactly ONE compiled: one build log holds `xcodebuild`, the other
  does not.
- Assert the waiter printed `<root> is already building <hash> (pid N)` and
  then `waited <d> for <root>'s build -> installed from cache`, and that its
  payload carries `waitedForBuild: { pid, ms }` with `cacheHit: "local"`.
- Two full compiles of one fingerprint is CRITICAL. A waiter that times out
  (`RN_ISO_BUILD_WAIT_TIMEOUT`) with the builder demonstrably alive is
  CRITICAL. A takeover line after a builder genuinely died is correct
  behaviour — quote it and move on.

### B8. `gc`'s view of all of it

```bash
npx rn-iso gc                       # report only. NEVER --delete without approval.
```

- Assert every cache above appears under `Shared build caches (N) - alive, not
garbage:` with a plausible size and the right directory: the Metro transform
  store, the Xcode compilation cache, the build cache, Metro file maps, and
  anything the project registered. Each row is tagged `(registered)` or
  `(detected)` — quote the block whole.
- Assert none of them is counted as reclaimable, and that a LIVE build shows
  under `Builds in progress (N) - NOT touched, by anything:` while it runs.
- If (and only if) the user approves: `gc --delete --older-than 90` and assert
  it removed only entries it named, that the atomic CAS was skipped with
  `index-backed; empty it whole or not at all`, and that a subsequent build in
  a live workspace still works. A cache that a live workspace depends on being
  removed is CRITICAL.

## C. Release builds [MANUAL]

iOS: `npx rn-iso ios --configuration Release --json`.
Android: `npx rn-iso android --variant <flavor>Release --json` (any variant
whose name ends in `Release` selects the release path; there is no separate
flag).

### C1. Metro is skipped entirely

- Assert the phase line: iOS/Android both print
  `metro  skipped (<variant/configuration>: the JS bundle is embedded, no dev
server is used)`.
- Assert the payload's `metroPort` is **null**.
- Assert no `adb reverse`, no `debug_http_host`, no dev-client deep link on
  Android; no Metro gate failure on either even with no dev server running at
  all (try it with `stop` first — a release build must not need one).
- A release run that reserves or requires a Metro port is CRITICAL: it means
  the release path is not actually release-shaped.

### C2. `launched` is proven by process liveness

On a release build there is no bundle request to observe, so `true` means the
app process was ALIVE a moment after launch (Android: `adb shell pidof
<package>`). Assert `launched: true` and quote the launch phase line
(`launched <package> on <serial> (<variant>, embedded JS bundle, no Metro)`).
A release app that dies at startup usually crashed loading its embedded
bundle — `rn-iso logs --errors` has the device log that says why.

### C3. iOS on a cache hit: the installed app runs THIS tree's JS

The build cache is keyed on the NATIVE fingerprint, so a release hit is an
`.app` carrying its BUILDER's JS. rn-iso swaps this tree's JS into a copy.
Prove it with a sentinel:

```bash
# in wt2, at the same commit, with a release entry already in the cache
echo "console.log('RN_ISO_SENTINEL_<unique>');" >> <the app entry file>
npx rn-iso ios --configuration Release --json > /tmp/qa-ios-rel.json
# the swapped app is the payload's appPath
APP=$(python3 -c 'import json,sys;print(json.load(open("/tmp/qa-ios-rel.json"))["appPath"])')
strings "$APP/main.jsbundle" | grep RN_ISO_SENTINEL_
```

- Assert the phase lines `js swap  regenerating this workspace's JS for the
cached Release app` and `js swap  hermes bytecode + assets replaced,
re-signed (<d>)`.
- Assert the sentinel is in the installed bundle. Hermes keeps string
  literals in its string table, so `strings | grep` works on bytecode too; if
  it does not, fall back to reading it on screen with your device tool.
- Restore the file afterwards; it is a tracked edit.
- A cached release app installed WITHOUT the swap is CRITICAL — that is
  silently running another workspace's code.
- A swap FAILURE that falls back to a full build is correct: quote the
  `js swap failed at <step>: <reason> -- building fresh instead` line and
  confirm the run still ended with this tree's JS.

### C4. Android on a cache hit: STORED, not deflated, and the asset gate

```bash
APK=$(python3 -c 'import json,sys;print(json.load(open("/tmp/qa-android-rel.json"))["appPath"])')
unzip -lv "$APK" | grep index.android.bundle
```

- Assert the bundle entry's method is **Stored**, not Defl. AGP stores it
  uncompressed so Hermes can mmap it; a deflated entry fails to load at
  runtime. Quote the `unzip -lv` row.
- Assert the phase line `apk swap  hermes bytecode repacked (store),
zipaligned and re-signed (<d>)`.
- **The asset gate.** Add a NEW asset to the tree (a png, `require`d from the
  app), rebuild against the same cache entry, and assert rn-iso REFUSES the
  swap and builds fresh:
  `apk swap  <reason> -- building fresh instead (an APK cannot be made to
carry an asset AAPT did not package)`. Then assert the fresh build REPLACED
  the entry (it must carry a new `assets-manifest.json`), so the next run does
  not hit the same refusal forever.
- An entry with no `assets-manifest.json` is never swapped at all — that is
  correct, and it is why B1 checks for the sidecar.
- A swap that proceeds despite a changed asset set is CRITICAL: the installed
  app's JS references an asset the APK does not carry.

## D. Android flavors [MANUAL]

Needs a repo with real product flavors. If none is available, say so — do not
manufacture one and call it covered.

```bash
npx rn-iso android --variant <flavor>Debug --json
```

- Assert gradle ran `assemble<Flavor>Debug` (capture the argv as in A6).
- Assert the APK was found in the FLAVOR's output directory
  (`android/app/build/outputs/apk/<flavor>/debug/`) with no manual
  intervention, and that `appPath` in the payload points there.
- Assert the applicationId came from the BUILT APK, not from the gradle files:
  the launch phase prints `applicationId <id> (from the APK; project files say
<other>)` when they differ, and installs/launches the APK's id either way.
- Assert `variant` in the payload echoes what you passed, and that the cache
  key is per-variant: build two variants at one commit and assert the second
  is a MISS, not a hit on the first's artifact.
- Assert the `android.variant` SETTING gives the same result as the flag, and
  that the flag wins when both are present.
- Ambiguity is a designed refusal, not a bug: a build that leaves several
  debug APKs and nothing to choose between them fails with
  `... and nothing says which flavor to install.` Quote it if you see it.
- A flavored build that installs the wrong flavor's APK, or reads the id from
  `build.gradle` when the APK says otherwise, is CRITICAL.

## E. The four `launched` values

`launched` is four-valued. Know which are pass conditions before you report
one.

| Value          | Means                                                                                                                                                              | Verdict                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `true`         | a bundle request from THIS workspace's Metro was observed — or, on a release build, the app process was alive after launch                                         | PASS                                                                                                                                                                                   |
| `"bundling"`   | the app asked this workspace's Metro for its bundle and Metro was still building it when the ~20s window closed. The wiring is proven; the JS has just not run yet | PASS                                                                                                                                                                                   |
| `"unverified"` | the app launched and NOTHING was observed. Usually a picker awaiting a tap or a confirmation alert                                                                 | NOT a pass on its own. Follow rn-iso's own stderr guidance, confirm by hand with your device tool, and report both the value and what you found. That fallback UX is itself under test |
| `false`        | it did not launch                                                                                                                                                  | FAIL                                                                                                                                                                                   |

A `true` on a run where you can see the app is NOT running is the worst
outcome in this document: rn-iso reporting success for something that failed.
CRITICAL, always.

## Severity

- **CRITICAL:** the documented loop cannot complete unassisted; rn-iso
  reported success for something that failed; wrong-workspace
  cross-contamination of any kind; a cache that is ENGAGED and does not
  STORE (the silent no-op); a release build that installs another
  workspace's JS; two compiles of one fingerprint.
- **HIGH:** a wrong or unactionable error message; a query that hides real
  signal; destructive-path surprises; a cache that stores but is never
  REUSED; `pod install` on every build of an unchanged tree.
- **MED:** false positives/negatives in doctor/init-class checks; misleading
  defaults; evidence that exists but is awkward to get at (the Android argv
  asymmetry in A6 is this).
- **LOW / papercut:** noise, cosmetics, missing progress output, a dim note
  that could say more.

## The friction log (the primary deliverable)

Number every finding. For each: **severity**, the **verbatim evidence** (the
exact output line, not a paraphrase), and a **one-line suggested fix**.
Classify honestly against the list above.

## Release QA matrix

The minimum combinations to exercise before a release. `RELEASE.md` makes this
a pre-tag gate.

| #   | Repo shape                                   | Platform                                                       | Patch                                                 | Minor    | What only this combination proves                                                                                         |
| --- | -------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------- |
| 1   | Fresh Expo app (`create-expo-app`)           | iOS                                                            | required (run the automated 2x2, not by hand)         | required | the baseline loop, on the fixture CI uses                                                                                 |
| 2   | Real monorepo, Expo, hoisted deps            | iOS                                                            | required                                              | required | prebuild against a committed config, Pods reuse (B6), the CAS (A5/B4), the remote tier (B2), dev-client scheme resolution |
| 3   | Real repo, flavored if one is available      | Android                                                        | required IF the release touches Android or any cache  | required | Gradle `--build-cache` + `FROM-CACHE` (A6/B5), flavors (D), applicationId from the APK                                    |
| 4   | Bare RN app                                  | iOS or Android                                                 | not required                                          | required | `bare-inproc` Metro store append (A4), the no-`@expo/fingerprint` refusal path                                            |
| 5   | Release build                                | iOS or Android (both on a minor that touches the release path) | required IF the release touches the release/swap path | required | `metroPort: null`, the JS sentinel (C3), STORED-not-deflated + the asset gate (C4)                                        |
| 6   | Two workspaces racing one fingerprint        | either                                                         | not required                                          | required | single-flight with a REAL compiler (B7) — CI only proves it with synthetic artifacts                                      |
| 7   | `gc` report over everything the pass created | either                                                         | required                                              | required | that no live cache is classified as garbage (B8)                                                                          |

Rules:

- **Patch:** rows 1, 2, 7, plus every row the patch's own changes touch.
  A patch that changes nothing outside the CLI's argument parsing may stop at
  rows 1, 2 and 7.
- **Minor:** every row.
- **A claim added by the release must have a step that proves it.** A release
  that adds a cache must show that cache GROWING (question 2 of B's three) and
  being REUSED (question 3) — not merely that its flag is on a command line.
  If the release adds a claim this protocol has no step for, ADD THE STEP
  before tagging. The protocol is the gate; a claim with no step is an
  unreleasable claim.
- Any CRITICAL finding blocks the tag. HIGH findings block unless the release
  notes name them.

## Report structure

(a) friction log; (b) what worked cleanly (be specific — this calibrates
trust); (c) timings table (setup, cold build, cached run, teardown);
(d) **the B table, filled in** — every cache, all three columns, with the
numbers; (e) the zero-config evidence from section A (the porcelain diff, the
`snap` pairs, the quoted argv lines); (f) release/flavor results if run, or an
explicit "not run, because ..."; (g) device-interaction evidence; (h) the five
cleanup checks with output; (i) outright BUGS with minimal repro, separate
from frictions; (j) which QA-matrix rows were exercised and which were not;
(k) the repo's shape (Expo/bare, SDK, package manager, mono/single, flavored
or not) so results are comparable across repos.
